# 乐饮 UC-RD-001｜从客户需求到可送样配方

这是一份给配方 Agent 的业务作业书。无论由哪一种 Agent、Workflow 或 Runtime 执行，都必须让乐饮的销售、配方师和杯测负责人看到他们熟悉的业务单据，而不是让人填写 `run_id`、哈希、证据编号或模型参数。

## 1. 这件事做到什么才算完成

使用者把一张客户需求单或一个客户标样交进来。系统结合当前豆批、历史配方、历史试验、库存和成本，帮助配方师形成首轮配方与小样任务；小样完成后，再根据真实杯测和实际饮用场景的结果，给出明确的“送客户确认 / 调整后再试 / 停止本方案”建议。

```text
客户需求或标样
        │
        ├─ 关键信息不足 ──> 需求补充单 ──> 回到入口
        │
        └─ 信息足够
              ↓
       当前豆批与历史经验匹配
        │                 │
        │                 └─ 缺豆、缺检验或批次不可用 ──> 寻源/补检清单
        ↓
       首轮配方方案单（A/B/C 只是可能，不强行凑数）
              ↓
       小样任务单与盲码
              ↓
       真实烘焙、杯测、应用测试
        │          │          │
        │          │          └─ 结果不可比 ──> 重测
        │          └─ 未达到目标 ──> 只改有证据支持的变量，再打一轮
        └─ 达到目标 ──> 配方师确认 ──> 送客户确认
```

本 UC 的终点是“形成可追溯、可复做、可送客户确认的小样方案”。以下事项不在本 UC 内：

- 正式报价与商务条款；
- 客户已经确认；
- 小样参数直接放大为大机参数；
- 量产 BOM、生产投料或放行。

## 2. 谁提供什么

### 2.1 销售或需求承接人提供

只提供客户真正表达过的内容：

| 业务问题 | 可接受的填写方式 |
|---|---|
| 要开发什么 | 熟豆拼配、咖啡液、冻干粉等；本 UC 只承接熟豆拼配 |
| 最终怎么喝或怎么用 | 黑咖、奶咖、后续萃取、冻干等，写清配方和杯量条件 |
| 客户想卖什么 | 100% 阿拉比卡、产地、风味、功能或价格带等卖点 |
| 客户想要什么感觉 | 尽量保留原话，例如“奶里还能喝到巧克力和烤坚果” |
| 客户绝不能接受什么 | 例如焦苦、发酵味突出、酸感突出 |
| 价格边界是什么 | 已确认的原料成本上限，或已批准的倒推口径；没有就写“待确认” |
| 有没有标样 | 有则附标样编号和分析记录；没有则明确写无 |
| 什么时候要样 | 日期或客户承诺时间 |
| 谁确认了这张需求单 | 人名/角色和原始沟通记录位置 |

不得把销售的猜测写成客户要求。不能影响配方方向的缺项可以标记后继续；会改变原料、风味、成本或最终用途的缺项必须先退回补充。

### 2.2 系统自动准备，不能让客户手填

- 当前可用生豆的物料名称、批次、库存、成本、准入状态、理化和批次杯测结果；
- 与本次用途相近的历史配方，以及当时的批次、烘焙、预期、实测和最终决定；
- 失败或偏差记录，尤其是“不好喝、成本超限、风味互相干扰、工艺不稳定”的记录；
- 当前可用小样机、批量、烘焙记录方式、杯测 SOP 和实际饮用场景测试方法；
- 客户已确认的标样分析结果；没有分析结果时不得假装已经理解标样。

咖啡豆是农业原料。同名物料的历史结果不能替代当前批次检验，上一批好喝不代表这一批可以直接使用。

## 3. Agent 必须怎样工作

### 3.1 先把客户原话翻译成可验证目标

输出《需求承接单》，并逐项区分：

- `必须满足`：不满足就不能进入送样；
- `希望满足`：用于比较候选，不得冒充硬约束；
- `待确认`：现在没有证据，不能替客户补答案；
- `评价方式`：在哪个饮用场景、由谁、怎样判断。

例如，“奶里还能喝到巧克力和烤坚果”应落为“按约定奶咖配方制作后，巧克力和烤坚果均达到已确认的‘清晰可辨’档位”；不能擅自改写成一个客户从未确认的 4.2 分。

标样入口必须先形成《标样分析记录》：样品身份、到样状态、豆型或配方线索、理化、标准化黑咖描述、实际用途表现和无法判断的部分。只看包装或产地猜配方不算分析。

### 3.2 查历史时，先判断能不能复用

每条历史记录必须比较：

1. 最终用途是否相同；
2. 客户目标和禁忌是否相同；
3. 原料规格与当前批次是否相同；
4. 烘焙方向和设备是否相同；
5. 评价方法是否可比；
6. 当时的预期与实测偏差是什么。

只允许复用“在这些条件下观察到什么、因此本轮值得验证什么”。不得把历史结论直接宣布为当前事实。

### 3.3 形成首轮方案，不为凑数而造方案

根据需求可以是单豆，也可以是拼配；可以有 A/B/C，也可以只有两个真正有区分度的候选。每个候选必须写清：

- 这个方案想解决什么；
- 使用哪些当前批次、各占多少；显示比例必须合计 100%；
- 每个样品实际领用多少；
- 建议的烘焙方向，以及它要验证的作用；
- 在目标饮用场景中预计出现什么，不确定在哪里；
- 当前批次证据和可复用的历史证据；
- 原料成本、库存、供应或工艺风险；
- 哪个观察结果会推翻这个方案。

两个候选如果只是在无业务理由的情况下把比例微调 1%，视为同一个方案。预计风味永远是“待试验假设”，不能写成“已达到”。

### 3.4 生成一张配方师可以直接执行的小样任务单

任务单必须让配方师不再追问即可开工：

- 样品盲码；
- 方案版本；
- 生豆物料、当前批次、比例和本次实际用量；
- 小样机和烘焙方向；
- 本样只验证哪个变量；
- 烘焙曲线或设备记录保存位置；
- 计划杯测时间和养豆条件；
- 标准化黑咖评价方法；
- 客户实际饮用场景的制作方法；
- 评价人和原始记录入口。

缺原料时输出《寻源/补检清单》，写清缺什么、为什么影响方案、找什么规格、补齐后从哪一步继续。缺料方案不能混进当轮可执行样品。

### 3.5 真实试验后再作结论

Runtime 必须暂停，等待烘焙、理化、杯测和实际饮用场景记录回填。禁止由模型编造“模拟杯测”冒充真实结果。

回填必须保留每位评价人的原始记录，不先平均。至少分别记录：

- 标准化黑咖：香气、风味、质地、余韵和缺陷描述；
- 实际用途：是否符合客户卖点和饮用场景，喜欢/不喜欢或适配判断；
- 样品、批次、设备、烘焙和制作条件；
- 与预测一致和不一致的地方。

标准化黑咖描述和奶咖适配是两件事。前者回答“杯中出现了什么”，后者回答“这个客户的产品是否合适”，不能压成一个总分。

如果评价条件不一致、样品身份对不上、原始记录缺失或评价人意见出现关键冲突，结论只能是“结果不可用，需要重测”。

物理结果回填至少使用以下业务字段，字段可以由系统从扫码记录和评价表自动带入：

| 回填内容 | 必须记录 |
|---|---|
| 样品身份 | 盲码、方案版本、实际物料批次 |
| 实际烘焙 | 设备、曲线/记录位置、实际偏离、烘焙日期 |
| 评价条件 | 养豆时间、研磨、水、水温、比例、器具，以及实际用途配方 |
| 黑咖原始记录 | 每位评价人的香气、风味、质地、余韵、缺陷描述 |
| 应用测试原始记录 | 每位评价人对客户每项必须条件、希望条件和禁忌的判断 |
| 异常 | 样品、设备、环境、顺序或记录异常；没有也要写“无” |

### 3.6 把结果变成下一步

输出《配方复盘单》，每个候选只能落到以下一种业务决定：

- `建议送客户确认`：所有必须条件已满足，配方责任人尚需签字；
- `调整后再试`：指出哪个实测偏差，下一轮只改哪个主要变量，预期改善什么；
- `先寻源或补检`：方案方向可保留，但当前不能执行；
- `停止本方案`：已被实测或硬约束推翻；
- `结果不可用，重测`：本轮没有形成可信判断。

每次复盘都要记录“原来怎样预期、实际发生了什么、这次学到了什么、适用边界是什么”。客户确认与量产授权仍由人完成。

## 4. 业务输出物

一次运行最多形成以下五张单，不生成无关报告：

### 4.1 《需求承接单》

必须包含：

- 客户原话；
- 产品形态与实际用途；
- 必须满足、希望满足、禁忌三张清单；
- 每项要求的评价场景和通过方式；
- 价格边界及其口径；
- 标样情况；
- 待确认问题及其业务影响；
- 原始沟通位置和需求确认人。

### 4.2 《首轮配方方案单》

每个候选必须包含：

- 方案名称和业务意图；
- 原料名称、当前批次、显示比例和每样领用量；
- 建议烘焙方向；
- 对客户必须条件、希望条件和禁忌的逐项预测；
- 当前豆批证据、历史经验和不适用边界；
- 加权生豆成本、库存和供应状态；
- 本轮要验证的问题及推翻条件；
- `可进入本轮 / 需寻源 / 需补检 / 已排除` 之一。

### 4.3 《小样任务单》

必须包含：

- 每个物理样的盲码、方案版本和唯一比较变量；
- 逐原料领料清单、批次和用量；
- 小样机、烘焙方向、曲线保存位置；
- 当前批次与烘焙方向对应的养豆条件；
- 标准化黑咖和实际用途的制作方法；
- 评价人、计划时间和原始记录入口；
- 配方师确认位。

它必须可以直接下发给执行人员。任何必填项是“待定”时，状态不能是 `待打样`。

### 4.4 《杯测与应用测试记录单》

必须包含：

- 实际样品、烘焙、养豆和制作条件；
- 每位评价人的标准化黑咖原始描述；
- 每位评价人对客户要求的逐项应用测试判断；
- 预测与实测的逐项对照；
- 评价分歧、异常和是否需要重测；
- 原始记录位置；模型汇总不得覆盖原始记录。

### 4.5 《配方复盘单》

必须包含：

- 客户必须条件、希望条件和禁忌的逐项结论；
- 预测与实测偏差；
- 每个候选唯一的业务决定；
- 下一轮唯一主要变量、保持不变项和反证条件；
- 可复用知识及适用边界；
- 下一步负责人和时间；
- 配方责任人签署位。

## 5. 业务界面显示的状态

| 状态 | 业务含义 |
|---|---|
| `待补需求` | 缺少会改变方案方向的信息 |
| `待寻源或补检` | 方案有方向，但当前豆批/检验不足 |
| `待打样` | 配方和任务单完整，可以开始做样 |
| `待录入试验结果` | 物理试验尚未回填 |
| `试验无效，待重测` | 结果身份、条件或记录不足以判断 |
| `待下一轮调整` | 实测未达目标，已有明确修订动作 |
| `待配方师确认送样` | 本轮达到约定目标，等待责任人签字 |

不得出现“客户已确认”“可以量产”之类超出权限的状态。

## 6. 数据与事实纪律

每条重要信息只允许属于以下一种：

- `客户已确认`：有客户或需求承接人的原始记录；
- `乐饮实测`：有样品、批次、设备、方法和日期；
- `行业方法`：有公开标准来源，只约束方法，不替客户定义好坏；
- `模拟数据`：只用于演示，不得写回真实业务；
- `待试验假设`：Agent 的推断，必须写反证条件。

不得用“行业通常如此”补造客户需求，不得用产地印象补造当前批次风味，不得把加权生豆成本叫完整成本或报价。

## 8. 来源与适用边界

- 乐饮昆山走访：客户需求按价格段、风味、卖点拆解，可能形成多个配方方案；缺料进入寻源；需求单和标样是两种入口；预测与实测要持续记录。
- 乐饮昆山走访：小样软件已记录拼配、设备界面和二维码；对比需保持研磨、水温、过滤等条件一致，并由多名有辨识能力的人判断。
- 2026-07-04 乐饮会议：产品开发从客户需求到样品确认，原料选择围绕价值/卖点、价格和用途，并复用历史试验、规避风味干扰与工艺不稳定。
- 2026-08-05 乐饮会议：一期目标是让配方人员在需求单、历史配方、理化、口感/风味评测和当前库存基础上，更快得到可工作的配方初稿。
- [SCA Coffee Value Assessment](https://sca.coffee/value-assessment/)：物理、描述性、偏好/情感和外在信息分开评价，不依赖单一总分。
- [SCA Coffee Standards](https://sca.coffee/research/coffee-standards/)：SCA-102 约束样品准备与品尝机制，SCA-103/104 分别对应描述性与偏好/情感评价。
- [WCR Sensory Lexicon](https://worldcoffeeresearch.org/resources/sensory-lexicon)：提供风味、香气和质地的统一描述词与强度参照；它不替客户决定什么风味是“好”。
